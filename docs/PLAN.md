# Plan: 个人 AI 分身站(面试官可先聊再面)

_Locked via grill — by the agent + user_

## Goal

把 `E:\WorkBuddy\rag-kb-demo`(RAG 知识库问答系统)改造为一个**个人 AI 分身网站**:用结构化 Markdown 知识库"蒸馏"用户的真实经历(简历 + 项目),部署到公开 URL;投简历时面试官先访问网站——首页一页式浏览简历(简介/技能/项目/经历),随后与以**第一人称"我是本人"**口吻回答的 AI 分身对话,可深度追问项目细节、技术方案、行为问题;回答**只基于知识库事实,不编造**,超出范围礼貌说明。上线前以"面试官高频问题"评测集(30-50 题,通过率 ≥90%)把关。

## Approach

1. **建仓**:新建仓库 `personal-agent-site`(公开;仓库不含手机号/邮箱/地址等个人信息与任何密钥),rag-kb-demo 留作参考源。后端从 rag-kb-demo 拷贝并改造,前端全新设计。
2. **后端改造(复用 rag-kb-demo backend)**:
   - 保留:Markdown 分块、混合检索(RRF)、Rerank、SSE 流式、Agent 多步问答(检索→反思→再检索)、问答日志(qa_log 匿名落库;公开历史接口移除)、反馈、评测、JWT。
   - 新增:**AI 分身系统人设**(第一人称、只答知识库事实、纯中文、语言不切换);**启动时 seed 知识库**(`resources/kb/*.md` 幂等灌入,按 doc 名/content hash 去重,重启不重复入库);**敏感词护栏**(仅拦"索取本人隐私"意图:薪资/身份证/联系方式等;密码/验证码/微信等技术词不拦,提示词级拒答 + 输出脱敏兜底);**每 IP 限流**(内存计数,默认 50 问/小时——留 NAT 共用出口余量,超过返回友好提示;登录接口单独 10 次/小时防爆破);**Agent 模式对访客开放**(默认开启,前端做好流式输出与思考步骤动效)。
   - 隐藏管理功能:文档上传、反馈统计、评测页面不暴露给访客;保留接口,站长经隐藏管理页(现有 JWT 登录)查看访客提问历史与反馈。
3. **内容蒸馏(第一阶段测试:fitlog-backend + rag-kb-demo)**:
   - 我(agent)起草:①蒸馏模板(每篇 md 的结构规范);②知识库 6 篇骨架(01-个人简介 / 02-教育背景 / 03-实习工作经历 / 04-项目经历 / 05-技能栈 / 06-常见面试问答 FAQ);③fitlog-backend、rag-kb-demo 两篇项目深挖初稿(背景/职责/技术难点/方案/量化成果/面试官可追问点)。
   - 用户提供:**真实简历数据**(替换占位数据,如 config 中的 张三→真名、教育/经历/联系方式由用户决定放哪些上站);审改项目深挖 md。其余项目(如 fitness-miniprogram、cross-border-demo)由用户后续自行选择补充。
4. **前端全新设计(Vue3 + Vite + TS + Pinia,沿用 rag-kb-demo 的 SSE 解析/Agent 动效代码)**:
   - 落地页:一页式简历(简介/技能/项目/经历/联系方式入口)+ 醒目"向 TA 提问"CTA,访客免登录。
   - 聊天页:全新视觉,SSE 流式打字、Agent 思考步骤动效、引用来源面板、示例提问 chip。
   - 管理页:隐藏入口 + JWT 登录,展示访客提问记录、反馈点赞/点踩、统计。
   - 纯中文界面。
5. **质量门槛**:建 30-50 题"面试官高频问题"评测集(自我介绍 / 项目深挖 / 技术八股 / 行为题各一批),跑现有 EvalService(Recall@K + LLM-as-judge),差评题逐个修知识库或 FAQ,通过率 ≥90% 再对外。
6. **部署**:购置**香港轻量服务器**(免 ICP 备案,约 ¥300-400/年)+ 域名(约 ¥50/年);服务器上 docker compose 起 PostgreSQL(pgvector)+ 后端/前端镜像(**CI 构建推 GHCR,2C2G 服务器只 pull 不在本机构建**),Nginx 反代 + HTTPS(certbot);域名 **zhengziheng.me**(裸域+www 均解析均服务)。联系信息经部署环境变量注入,不进仓库。
7. **上线检查清单**:轮换/作废 rag-kb-demo `.env.example` 中已提交的 DeepSeek key;确认仓库无个人信息与密钥;限流与敏感词护栏生效;管理页鉴权有效;埋点(可选:统计访客问题类型)。

## Key decisions & tradeoffs

- **复用后端、藏管理功能(而非瘦身删模块)**:改造快、回归风险低(45+10 测试在),代价是后端保留若干访客不可见的接口/表——由前端路由不暴露 + 接口保留但管理页才用,接受"代码里有多余面"。
- **Agent 模式默认对访客开放**:这是技术亮点(ReAct 多步 + 思考动效),代价是每问多次 LLM 调用、响应变慢(10-30s)、成本上升——用每 IP 限流 + 单次 token 上限兜底。
- **第一人称 + 只答事实 + 敏感词护栏**:可信度优先,回答克制;代价是开放性问题(如"你觉得自己最大的缺点是什么")若知识库没写,回答会偏保守,可能显得"官方"——靠 FAQ 骨架引导用户预写这类题。
- **Embedding 用硅基流动 bge-m3(OpenAI 兼容),本地 hash 兜底**:中文检索质量优先;DeepSeek 无 Embedding 接口故不可用。兜底保留保证无 key 也能跑,但上线必须配真 Embedding。
- **内存限流(非 Redis)**:单机单实例足够,避免引入中间件;多实例/重启后计数丢失可接受。
- **seed 幂等**:按 doc 名/content hash 去重,避免重启重复灌入;文档更新需手动触发(如重建 doc 或按 hash 变更重灌)。
- **公开仓库 + 个人信息隔离**:代码公开增强可信度,但联系信息/密钥绝不入库;知识库经历内容本身即网站对外内容,放仓库无妨,但联系字段走部署环境变量。
- **香港服务器免备案**:当天可用,国内访问速度"良好但不极致";对投简历场景可接受。
- **LLM-as-judge 用 DeepSeek 当裁判**:与作答模型同源,存在自我偏好偏差;评测集需人工复核差评题,不能全信 judge。

## Risks / open questions

- **前置依赖:用户需提供真实简历数据**,否则落地页与知识库仍是占位;计划先以 fitlog/rag 项目蒸馏跑通管线,简历数据到位后补填。
- **fitlog-backend 仓库文档完整度未知**:若 README/注释不足,蒸馏初稿质量受限,需用户补口述。
- **域名待注册**:已定 zhengziheng.me(阿里云,.me 后缀);上线前需用户完成注册 + 实名认证(约几小时)。
- **LLM-as-judge 可靠性**:若 judge 对部分题误判,可能误伤达标判定;评测报告需人工抽查。
- **限流误伤**:面试官同办公室共用出口 IP 可能触发限流;需在友好提示中引导(如"请稍后再试"),必要时放宽阈值。

## Out of scope

- 多语言(纯中文,不做中英切换)。
- 更换技术栈(不换 React/Next.js;不换后端语言)。
- 三个旧简历站(resume-original/-website/-website-new)的代码迁移,仅按需提取素材(头像/截图);新站取代它们。
- 真实简历之外的项目深挖(除 fitlog/rag 外,由用户后续自行选择补充)。
- 移动端原生 App、小程序版。
- 本地离线演示环境(直接面向线上部署)。
- 面试官身份识别、访客注册/登录(访客全程匿名免登录)。
