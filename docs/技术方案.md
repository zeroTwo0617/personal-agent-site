- 纯中文、访客匿名免登录;管理功能走 JWT。

### 4.2 AI 分身人设(核心修改)

**normal 模式**(替换 `ChatTaskService.runTask` 中的 system 提示词):

```
你是「郑梓恒」的 AI 分身,一名 Java/Go 后端方向的求职者,正在与面试官/HR 对话。
回答规则:
1. 始终以第一人称「我(郑梓恒)」自然、专业、自信地作答,像候选人本人;
2. 只能依据【上下文】中检索到的简历/项目经历事实回答,绝不编造;上下文没有的信息,
   如实说「我的简历/经历中没有这方面的内容,建议直接问我本人」;
3. 全程使用中文;
4. 仅当对方**索取本人的隐私信息**(薪资期望、身份证号、手机号、联系方式等)时,礼貌拒答并引导「这类信息建议与本人直接沟通」;
   技术性提问(如"密码如何加密存储""验证码怎么防刷")是正常面试题,照常回答;
5. 结构清晰:先结论后要点;涉及项目时给出具体细节(背景/难点/方案/量化成果);
6. 末尾用 [N] 标注引用来源,与【来源N】一一对应。
```

**agent 模式**(在 `AgentChatService.buildSystemPrompt()` 开头插入同一人设段,保留 THOUGHT/ACTION 格式约束与工具清单)。实现:抽一个 `PersonaPrompts` 常量类,两处引用,避免文案漂移;**人设中的名字取自配置 `app.persona-name`(默认"郑梓恒"——站点公开展示名,非法定真名,隐私无碍)**。

### 4.3 知识库 seed(`KbSeedService`,新增)

- 实现 `ApplicationRunner`:应用启动、数据库就绪后执行一次;
- 扫描目录:默认 `classpath:kb/*.md`(打进 jar);支持 `KB_DIR` 环境变量指向外部目录(便于不重新打包就改内容,重启生效);
- **幂等策略**:对每个文件计算 `SHA-256(content)`;查 `document` 表 `name = 文件名 AND content_hash = 摘要` → 命中则跳过;同名但摘要不同 → 删除旧文档(级联删 chunk)后重灌;新增文件 → 直接灌;
- 灌入流程复用 `DocumentIngestService` 的解析→分块→embedding→写库逻辑(将其 `ingest(MultipartFile)` 重构出 `ingestContent(String name, String content)` 供 seed 与上传共用);
- 失败处理:seed 失败记 ERROR 日志、服务继续启动;聊天接口在知识库为空时返回友好提示;管理页可查状态并手动重建;
- 管理接口:`POST /api/admin/kb/rebuild`(重扫重灌)、`GET /api/admin/kb/status`(文档数/分块数/上次 seed 时间)。

### 4.4 每 IP 限流(`RateLimitService` + `RateLimitInterceptor`,新增)

- 实现:内存滑动窗口 `ConcurrentHashMap<String, Deque<Long>>`(key=IP,value=时间戳队列);1 小时窗口内最多 N 次(默认 **50**,`rag.rate-limit.per-hour` 可配——阈值按"面试官深度追问一场 + 同公司 NAT 共用出口 IP"留足余量,成本侧由单次 token 上限兜底);超限返回 `429` + 友好 JSON `{"code":429,"message":"提问太频繁啦,请稍后再试"}`;
- **IP 获取**:部署在 Nginx 之后必须信任代理头——Nginx 配 `proxy_set_header X-Real-IP $remote_addr;`,后端取 `X-Real-IP`(无则 remoteAddr);拦截器注册到 `/api/chat`(提交问答)与 `/api/feedback`;SSE 流由 taskId 关联,不重复计数;
- **登录接口防爆破**:`/api/auth/login` 单独挂更严的限流(默认 **10 次/小时/IP**,`rag.rate-limit.login-per-hour` 可配),超限同样返回 429;该限制随 M1 限流一并实现,不留到"后补"——登录口公开且无验证码,不限流等于敞开暴力破解;
- 清理:定时任务每 5 分钟清空过期窗口(或惰性删除),防内存增长;
- 单实例内存即可(决策 Q:不引入 Redis)。

### 4.5 敏感词护栏(`SensitiveGuard`,新增)

- **输入侧拦截(仅"索取本人隐私"意图)**:命中明确索取隐私的**意图词 + 精确正则**才拦截——意图词(薪资|工资|待遇|期望薪酬|月薪|年薪)+ 精确模式(身份证 `\d{17}[\dXx]`、11 位手机号 `(?<!\d)1[3-9]\d{9}(?!\d)`);命中 → 不调 LLM,直接返回护栏话术(`"这类信息建议与本人直接沟通,面试时可以当面问。"`);
- **不拦技术词**:密码/验证码/微信/电话/邮箱等**普通名词不进输入词表**——否则会误杀"密码如何加密存储""验证码怎么防刷""微信小程序项目"等正经面试题;此类话题交给提示词级护栏(§4.2 规则 4)+ 输出侧脱敏兜底;
- **输出侧兜底**:LLM 回答后正则扫描(手机号 `(?<!\d)1[3-9]\d{9}(?!\d)`——**加前后边界,防误伤订单号/时间戳等长数字串**;邮箱;身份证 `\d{17}[\dXx]`),命中即脱敏为 `[联系方式已隐藏]`;
- 词表配置化:`rag.guard.sensitive-words`(**仅意图词**,逗号分隔,env 可覆盖),默认值见 application.yml;
- 目的:拦截"索要隐私"的无效请求(省钱)+ 防泄露 + **不误杀正经提问**。

### 4.6 鉴权改造(站长账号)

现状:`AuthService` 是**内存用户表 + 开放注册**(`register` 公开)。改造:

- 移除开放注册;`AuthService` 改为启动时从配置注入**单站长账号**:`security.admin.username`(默认 `admin`)+ `security.admin.password`(默认空,**生产必须 env 注入**;密码建议 BCrypt 哈希后存配置);
- 保留 `POST /api/auth/login`(站长登录拿 JWT);`POST /api/auth/register` 删除;
- **SecurityConfig 改造**:
  - CORS 白名单:`allowedOriginPatterns` 从 `*` 改为 **裸域 + www + 本地开发**(`https://zhengziheng.me`、`https://www.zhengziheng.me`、`http://localhost:5173`,可配 `app.cors-origins` 逗号分隔);
  - 路径规则:公开 = `/api/chat/**`、`/api/feedback`(POST)、`/api/auth/login`(公开但挂更严限流,见 §4.4)、`/api/chat/llm-status`;受保护 = `/api/admin/**`(需 JWT + 用户名 == 站长,新增 `JwtAuthFilter`);
  - 其余(`/api/documents/**`、`/api/eval/**`、`/api/feedback/stats`)默认 401(前端不再暴露入口,接口留作站长调试,可后续收紧)。

## 5. 前端详细设计(全新设计)

### 5.1 路由与页面

```
/        → LandingView   落地页(简历一页式 + CTA)
/chat    → ChatView      聊天页(与 AI 分身对话)
```

- 无访客登录态;管理页独立 token(localStorage,key 与访客隔离)。

### 5.2 落地页(LandingView)

- 模块(自上而下):**Hero**(头像/姓名/定位一句话/"向 TA 提问"CTA)/ **关于我** / **技能栈**(分类标签+熟练度)/ **项目**(卡片:标题/描述/技术栈/外链)/ **经历时间线**(实习/工作)/ **教育与其他**(竞赛等)/ **联系与页脚**(链接入口 + 隐私声明"本站为 AI 分身,内容基于本人简历与项目经历,以本人为准");

- 视觉:深色科技感主题 + 品牌主色(如靛蓝 #4F46E5);响应式(移动端单列);
- 参考素材:旧 resume 站的头像/项目截图可提取复用(决策:新站取代旧站,仅取素材)。

### 5.3 聊天页(ChatView,核心体验)

- 布局:左侧(可选)会话列表/设置,主区消息流 + 底部输入区;移动端单列;
- **流式输出**:移植 rag-kb-demo `api/chat.ts` 的 `openChatStream`(fetch + ReadableStream 解析 SSE),逐字渲染 + 光标闪烁;
- **Agent 思考动效**(重点打磨):收到 `agent_step` 事件(running/done)时,在回答前渲染**步骤时间线卡片**:`🔍 正在检索… → 命中 N 条 → 🔎 关键词检索 → 📄 读文档 → 💭 反思中 → ✍️ 组织答案`;步骤间平滑过渡动画;done 后折叠为"思考过程(点击展开)";
- 引用来源:done 事件携带 sources → 回答正文 [N] 锚点 + 底部**来源面板**(文档名/章节/相似度,可折叠);点击跳转对应章节;
- 示例提问 chips(首屏引导):"做个自我介绍""介绍一下你的 RAG 项目""你在项目里遇到过最大的困难是什么""为什么选择做 AI 分身站";
- **深度思考开关**(默认开):切换请求 mode=agent/normal;开关旁提示"深度思考更慢但更全面";
- 输入约束:≤500 字(前端计数+禁用);空输入禁用发送;输入侧敏感词轻量过滤(可选,后端为准);
- 多轮上下文:携带最近 ≤10 轮(store 自动截断);"新对话"按钮清空(localStorage 恢复逻辑照搬 rag-kb-demo chat store);
- 隐私声明页脚 + 限流提示兜底(429 时展示后端 message)。

### 5.4 管理页(AdminView)

- 登录表单(JWT)→ 面板:
  - **概览**:总问答数、今日问答、好评率、最近 7 天趋势(简单柱状);
  - **访客提问记录**:分页表格(问题/答案截断/时间/来源数),关键词搜索;
  - **反馈列表**:差评(问题原文+评论)高亮,一键复制到 FAQ 候选;
  - **知识库**:文档/分块数、上次 seed 时间、[重建索引] 按钮(确认弹窗);
- 接口对应 §4.7 管理清单;token 过期(86400s)自动跳登录。

### 5.5 状态与 API 层

- Pinia:复用 `chat store`(消息 + localStorage 恢复,换 key 命名 `pa-chat-history`);新增 `admin store`(token/统计/qa 列表);
- api 层:`request.ts`(axios 实例,baseURL `VITE_API_BASE`,拦截器带 token、统一错误码)→ `chat.ts`(移植 + mode 参数)/ `admin.ts`(新增)/ `feedback.ts`(保留);
- 类型:`types/index.ts` 照搬(Result/ChatTaskResult/AgentStepEvent/ChunkSearchResult 等)+ 新增 Admin 相关类型。

### 5.6 视觉设计原则

- 主题:深色为主(面试官观感:专业、科技、克制),主色靛蓝 + 渐变点缀;
- 字体:系统字体栈 + 代码风强调(mono 用于技术标签);
- 动效:流式打字、Agent 步骤过渡、来源展开;整体 <300ms 过渡,不喧宾夺主;
- 移动端:单列、触控友好(48px 点击区)、聊天输入区固定底部。

## 7. 评测设计

- 评测集:`eval/interview-questions.json`,结构:
  ```json
  [{ "id": 1, "category": "自我介绍", "question": "请做一下自我介绍",
     "expectKeywords": ["教育", "后端", "项目"], "reference": "要点:...", "maxScore": 5 }]
  ```
  共 30-50 题(自我介绍 5-8 / 项目深挖 10-15 / 八股 10-15 / 行为 5-10);
- 执行:复用 EvalService 逐题问答 → Recall@K(命中 expectKeywords 比例)+ LLM-as-judge 打分(DeepSeek 裁判,按 reference 判分 0-5)。**主跑 agent 模式(线上访客默认路径),并跑一轮 normal 作对照**,两侧均出报告;
- 通过标准:**agent 路径通过率 ≥90%**(得分 ≥4/5 计通过)为上线门槛 + **零"编造"类差评**(judge 标记"回答包含知识库外事实"即人工复核);normal 对照通过率 ≥90% 为质量基线(不阻塞上线,用于评估兜底路径);
- 迭代:差评题 → 定位(补 FAQ / 改知识库表述 / 调 topK / 换 rerank)→ 重跑;人工抽查 10 题确认 judge 无误判;
- 产出:HTML 报告(`target/eval-report.html`)+ 差评清单。

## 8. 部署设计

### 8.1 docker-compose(生产用镜像,不在服务器构建)

```yaml
services:
  pg:          # pgvector/pgvector:pg16,volume 持久化;2G 内存机调 shared_buffers
    command: ["postgres", "-c", "shared_buffers=256MB"]
  backend:     # ⚠️ 用 CI 构建好的镜像,服务器不构建(见 §8.2)
    image: ghcr.io/<owner>/personal-agent-backend:latest
    environment: # 同 §4.8 全量 env
    # JAVA_OPTS 由镜像 ENTRYPOINT 读取;-Xmx768m -Xms256m
    # ⚠️ 不映射宿主端口(仅容器内网,由 nginx 反代)——后端 8080 不对公网开放,
    #   否则 X-Real-IP 可被伪造绕过限流
    restart: unless-stopped
  nginx:       # 前端 dist 已打进镜像(CI 构建),无需挂载宿主机目录
    image: ghcr.io/zerotwo0617/personal-agent-frontend:latest   # CI 构建，dist 内置
    ports: ["80:80", "443:443"]
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - certbot-webroot:/var/www/certbot
      - certbot-certs:/etc/letsencrypt
    depends_on: [backend]
    restart: unless-stopped
```

> 本地开发(内存充足的机器)仍可用 `docker compose -f deploy/docker-compose.local.yml up --build`(local 版保留 `build:` 指向);**生产服务器一律 `pull` 运行,不构建**。

> 内存预算(2C2G,**服务器零构建后**):JVM 堆 768m + PG shared_buffers 256MB + Nginx <50MB,合计 <1.5G;swap 仅兜底流量高峰(不再为构建兜底)。

### 8.2 构建与发布策略(CI 构建,服务器零构建)

**动机**:2C2G 上跑 Maven 多阶段构建/`vite build` 会 OOM(运行态已占 ~1.5G,构建 JVM 再吃 1G+);加 swap 只能把 OOM 变慢,不可靠。**构建一律放到 CI,服务器只拉镜像运行。**

- **CI(GitHub Actions,公开仓库免费)**:
  1. `backend` job:`mvn test`(含集成测试)→ `mvn -DskipTests package` → 多阶段 Dockerfile(构建阶段 Maven,运行阶段仅 JRE+jar)→ push `ghcr.io/<owner>/personal-agent-backend:<sha|latest>`;
  2. `frontend` job:`npm test` + `vue-tsc -b` + `vite build` → 多阶段 Dockerfile(node 构建 → nginx 镜像 **内置 dist**)→ push `ghcr.io/zerotwo0617/personal-agent-frontend:<sha|latest>`;
  3. 触发:push main / 手动;tag 打 `latest` 供服务器拉取。
- **服务器(2C2G)**:
  - **不装 Maven / Node / 不做 `docker build`**(部署步骤明示,见 §8.4);
  - 只 `docker compose pull && docker compose up -d`(或 watchtower 自动更新,可选);
- **镜像仓库**:优先 **GHCR**(与公开仓库同源,免额外账号);若香港服务器拉取 ghcr.io 慢,备选 Docker Hub 或国内镜像加速;
  - 注意:GHCR package **公开时可匿名 pull**;若仓库/package 设为私有,服务器需先 `docker login ghcr.io`(PAT,`read:packages` 权限)——上线步骤 §8.4 需含此步;
- **回滚**:`docker compose up -d` 指定上一版镜像 tag,秒级回滚;镜像带版本 tag,不覆盖式发布。

### 8.3 Nginx 要点

```nginx
server {
  listen 80; server_name zhengziheng.me www.zhengziheng.me;
  location /.well-known/acme-challenge/ { root /var/www/certbot; }
  location / { return 301 https://$host$request_uri; }
}
server {
  listen 443 ssl; # certbot 注入证书路径
  root /usr/share/nginx/html;
  location /api/ {
    proxy_pass http://backend:8080;
    proxy_set_header X-Real-IP $remote_addr;   # ★ 限流取真实 IP 的关键
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_buffering off;                        # ★ SSE 必须关缓冲
    proxy_read_timeout 120s;
  }
  location / { try_files $uri $uri/ /index.html; }   # SPA fallback
}
```

> 定稿:裸域 `zhengziheng.me` 与 `www.zhengziheng.me` **均解析、均服务**(不做 301 合并,保持简单);**证书签发必须同时 `-d zhengziheng.me -d www.zhengziheng.me`(SAN 覆盖两主机名)**,CORS 白名单与证书主机名保持一致(§4.6/§4.8)。

### 8.4 上线步骤(服务器就绪后)

1. 域名解析 `zhengziheng.me` + `www` A 记录 → 服务器 IP;安全组**仅放行 22/80/443**(后端 8080 不对外开放);
2. 服务器装 **Docker(仅此而已:不装 Maven/Node,不在服务器构建镜像)** + 创建 1-2G swapfile(兜底流量高峰);`git clone` 仓库(**仅取 `deploy/` 的 compose/nginx.conf/env,不执行任何构建**)或直接 scp `deploy/` 目录;`cp deploy/.env.example .env` 填真实值;
3. certbot 以一次性容器运行(`docker run certbot/certbot`,webroot/证书卷挂载,**`-d zhengziheng.me -d www.zhengziheng.me` 覆盖两主机名**);续期用 cron 定期跑同一命令 + `docker compose exec nginx nginx -s reload`;
4. `docker compose pull && docker compose up -d`(CI 已推送镜像);验证:HTTPS(裸域+www)、聊天问答(**默认 agent** + 切换 normal)、限流(连发 51 问触发 429)、管理页登录;
5. 备份 cron:每日 `pg_dump` → 本地目录 + 可选 OSS 上传;**首次做一次恢复演练**。

## 9. 安全设计汇总

| 面 | 措施 |
|----|------|
| 密钥 | 全部 env 注入,仓库零密钥;旧 rag-kb-demo `.env.example` 泄露 key 作废轮换 |
| 个人信息 | 仓库无手机号/邮箱/地址;联系信息构建期注入;页脚隐私声明 |
| 传输 | 全站 HTTPS + 80→443 跳转 |
| 访问控制 | `/api/admin/**` 需 JWT 且用户名=站长;移除开放注册 |
| 滥用 | 每 IP 限流(50 问/时)+ 登录接口更严限流(10 次/时,防爆破)+ 单次 token 上限 + 输入 500 字限制 |
| 内容安全 | 敏感词护栏(输入仅拦"索取隐私"意图 + 输出脱敏)+ 人设"只答事实" |
| CORS | 白名单:裸域 + www + localhost:5173(原 `*` 收紧) |
| 端口暴露 | 后端 8080 仅容器内网(不映射宿主),公网只开 80/443;X-Real-IP 由 Nginx 注入,防伪造绕过限流 |
| 依赖 | Spring Boot 3.2 依赖升级到无已知 CVE 版本(mvn versions 校验) |
