# 开发问题记录（个人 AI 分身站）

> 本文件记录本项目开发期间遇到并解决的问题：现象 → 原因 → 解决 → 教训。
> 按类别组织；既是开发复盘，也是面试讲"项目难点/排障"的素材。

## 一、环境与工具链

### 1. Windows PowerShell 5.1 把 UTF-8 中文写坏（包名重命名事故）
- **现象**：用脚本批量把包名 `com.ragdemo` 改为 `me.zhengziheng.agent` 后，86 个文件的中文注释全部变成乱码（`鐭ヨ瘑搴...`）。
- **原因**：PS 5.1 的 `Get-Content` 默认按系统 ANSI（GBK）读文件，把 UTF-8 字节错读成 GBK 字符串，再 `Set-Content -Encoding utf8` 写回 → 双重编码损坏；且 5.1 的 `Set-Content` 不认 `utf8NoBOM` 枚举（那是 pwsh 7 的）。
- **解决**：删除损坏副本，重新字节级拷贝；改用 `[System.IO.File]::ReadAllText/WriteAllText` 显式 UTF-8（无 BOM）重做重命名，中文完好。
- **教训**：Windows 下任何批量文本操作必须显式指定 UTF-8 编码；改文件前先确认 PowerShell 版本语义。

### 2. Java 运行时残缺：加密策略目录缺失
- **现象**：后端一启动就崩：`Can't read cryptographic policy directory: unlimited`（`java.security.SecurityException`），`mvn clean` 也会触发。
- **原因**：`java.home = D:\`（JDK 被直接解压到 D 盘根目录），缺 `conf/security/policy/unlimited`；PG JDBC 的 SCRAM 认证、JWT 签名（HmacSHA256）都需要 JCE 加密策略。
- **解决**：找到完整 JDK（IntelliJ 自带 JBR 17，有 conf/security）；项目 `java.version` 19→17（Spring Boot 3 的 LTS 基线，代码全部兼容）。
- **教训**：环境里能 `mvn compile` 不代表 JDK 完整——加密/网络相关能力需要 `conf/security`；换环境先验证 JCE。

### 3. 8080 端口冲突导致启动失败
- **现象**：用户端 `Error starting ApplicationContext`，原因行被截断。
- **原因**：我后台跑的测试后端占着 8080，用户 IDEA 里再启动 → Tomcat 绑不上端口。
- **解决**：停掉我的实例释放 8080；后续验证用 8081（`SERVER_PORT` 环境变量）。
- **教训**：多实例/多环境跑服务必须错开端口；`LoggingFailureAnalysisReporter` 会输出具体原因，看它下面的 Description。

### 4. PowerShell 传 mvn 参数被解析坏
- **现象**：`mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8081` → `Unknown lifecycle phase ".run.arguments=--server.port=8081"`。
- **原因**：PS 对含 `--`/`=` 的 `-D` 参数处理有坑。
- **解决**：改用环境变量 `$env:SERVER_PORT = "8081"`（Spring Boot 原生支持）。
- **教训**：PS 里给 mvn 传复杂参数优先用环境变量。

## 二、Agent / RAG 行为

### 5. Agent 凭常识编造（不检索直接答）
- **现象**：agent 模式问"RAG 项目最难的点"，模型直接给答案，STEPS=0、SOURCES=0——没有检索知识库就作答。
- **原因**：DeepSeek 认为"信息足够"就直接输出 ANSWER（ReAct 格式允许），凭自身常识回答，而非从知识库检索。
- **解决**：① 提示词强制"回答任何问题前必须先 retrieve，严禁未检索直接 ANSWER"；② 代码级兜底——`forceRetrieve` 从"仅'未找到'时触发"泛化为"**任何未检索就作答**都强制补检索"。
- **教训**：ReAct 的"信息足够直接答"分支是幻觉高发点，必须提示词 + 代码双重约束。

### 6. agent 调"读取文档"返回 0 分块
- **现象**：agent 步骤显示"读取文档 → 文档共 0 个分块"。
- **原因**：检索结果上下文（`buildGlobalContext`）没暴露 docId，模型拿不到合法 ID 只能瞎传；且 GetDocumentTool 把来源名写死成 `docId=xxx`。
- **解决**：① 检索片段标注 `(docId=xxx)`；② **移除 get_document 工具**（小知识库下 retrieve 已够，消除失败模式）；③ GetDocumentTool 解析真实文档名 + docId 无效时明确指引"先 list_documents"。
- **教训**：工具契约必须暴露调用方需要的参数；价值边际低且频繁失败的工具，宁可从工具列表移除。

### 7. agent 最终答案非流式
- **现象**：normal 模式逐字流式，agent 模式答案"突然整段出现"（ReAct 循环用非流式 generate）。
- **解决**：收敛出最终答案后，用当前 messages **重新流式生成**（`streamFinalAnswer` 走 streamGenerate），逐字推 SSE delta；以流式文本为准（所见即所存），失败回退已解析答案。轮询接口同步更新进度。
- **代价**：最终答案那步"generate 判定 + streamGenerate 显示"两次调用，agent 每次多约 1 次 LLM 调用（单价低，可接受）。

### 8. 思考过程（reasoning_content）被丢弃
- **现象**：前端想展示模型"思考"过程（像 DeepSeek/ChatGPT 的 Think 块），但看不到——OpenAiLlmClient 只解析 `choices[0].delta.content`，丢弃 `reasoning_content`。
- **原因**：DeepSeek v4 思考模式产出的推理内容在 `reasoning_content` 字段，与答案 `content` 分开流式输出。
- **解决**：SSE 解析同时读 `reasoning_content` → `onThinking` 回调 → 后端推 `{"type":"thinking"}` 事件 → 前端渲染可折叠"💭 思考"块，思考中展开、答完自动收起。
- **教训**：DeepSeek v4 默认开思考是**静默行为变更**（旧 deepseek-chat 默认关），必须显式传 `thinking` 参数 + 解析 `reasoning_content`，否则延迟/成本悄悄上涨。

## 三、评测闭环

### 9. 评测口径与真实产品行为不一致（多轮迭代）
- **现象**：① 忠实度只有 45-60%；② reject 题全判"拒答失败"。
- **原因**（三个）：
  1. 评测用**泛化助手提示词**，不是人设 → 测得不是真实行为；
  2. **裁判过严**：二值判定，把"这个问题问得很好"等口语化表达也算不忠实（真实答案其实 grounded）；
  3. **拒答检测词表不全**：人设拒答措辞是"建议与本人直接沟通"，检测器只认"建议直接问我本人"。
- **解决**：① 评测改用 `PersonaPrompts.systemPrompt()`；② 裁判宽松化（忽略开场白/过渡句/语气词，只揪实质性编造）；③ `isRefusal` 补"个人隐私/与本人沟通/没有实习经历"等措辞。
- **效果**：忠实度 45-60% → 84-96%（LLM 非确定性导致波动，核心内容均 grounded）。

### 10. 八股题与"应拒答"评测矛盾
- **现象**：HashMap/TCP/Redis 等八股题被判"未拒答"失败。
- **原因**：人设规则说"技术性提问照常回答"（模型用自己的知识答八股），但评测集把八股设成 `expectRefusal: true`（期望拒答）——策略矛盾。
- **决策**（与用户确认）：**AI 用自身知识答八股**（候选人本来就会），八股题不再算拒答；评测集改为只测隐私/经历类拒答；人设规则 2 明确"个人事实只答知识库，通用技术知识可正常回答"。
- **教训**：评测集必须匹配真实产品决策；指标定义错了会误导优化方向。

### 11. 评测请求前端超时
- **现象**：管理页点"跑评测"→ `timeout of 30000ms exceeded`。
- **原因**：评测 28 题 × ~3 次 LLM 调用约 2-4 分钟，axios 默认 30s 超时。
- **解决**：`get/post` 支持按请求覆盖 timeout，评测请求单独设 600s。
- **教训**：长耗时接口（评测/批量）必须单独设超时，或改"异步任务 + 轮询"。

## 四、常规开发坑

### 12. 接口签名变更导致测试编译失败
- **现象**：`AgentChatService` 构造器加参数、`LlmClient` 加方法后，`AgentChatServiceTest` 编译失败。
- **解决**：更新测试（FakeLlm 实现新方法、构造器补参）；接口变更尽量留默认方法/重载减少破坏面。
- **教训**：改接口/构造器后先 `mvn test-compile` 验证测试层。

### 13. LlmClient 参数顺序写反
- **现象**：`streamGenerate(messages, "agent", lambda)` 编译报"String 无法转换为 Consumer"。
- **原因**：接口签名是 `(messages, onDelta, mode)`，调用时把 mode 和回调写反。
- **解决**：按签名调换参数。
- **教训**：多参数接口调用前先看签名；编译期就能发现，不用等到运行。

### 14. git 默认分支是 master 而非 main
- **现象**：`git checkout main` 报 pathspec 不存在。
- **原因**：`git init` 默认分支为 `master`。
- **解决**：合并到 `master`；如需 main 可 `git branch -m master main`。
- **教训**：建仓时先确认默认分支。

```powershell
# 查 8080/8081 端口占用

mvn spring-boot:run

# 批量改文本(显式 UTF-8,避免 GBK 乱码)
$enc = New-Object System.Text.UTF8Encoding($false)
$c = [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($path, $c.Replace("旧","新"), $enc)
```
